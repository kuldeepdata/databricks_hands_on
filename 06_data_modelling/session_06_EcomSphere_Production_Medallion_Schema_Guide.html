Production Medallion Architecture & Schema Guide

This guide shows how raw e-commerce data moves from Bronze to trusted Silver business entities and then into three Gold analytical models: a canonical Star Schema, a One Big Table, and Summary Marts. It also shows the metadata, quarantine and governance controls that make the pipeline safe to rerun, audit and operate.

1. How the pipeline is connected

Each layer has a different responsibility. Bronze protects source fidelity. Silver protects business correctness. Gold makes trusted data easy to consume. Supporting schemas keep the pipeline observable and recoverable.

SourcesOLTP / RDBMS
ADLS JSON feeds
→
BronzeRaw, append-oriented, source-aligned + technical metadata
→
SilverClean, standardised, deduplicated, validated and conformed
→
Gold CoreCanonical dimensions and facts
→
Gold ServingOne Big Table + Summary Marts
Important idea: the Star Schema is the canonical analytical model. The OBT and Summary Marts reuse the same trusted Gold measures so revenue, order counts and other KPIs do not get different definitions in different dashboards.

2. Layer responsibilities

Bronze — preserve

  • Keep all source columns.
  • Append records rather than updating raw history.
  • Add ingestion, CDC and lineage metadata.
  • Do not clean business values here.

Silver — trust

  • Standardise formats and codes.
  • Deduplicate and handle late data.
  • Validate references and business rules.
  • Integrate sources at clearly defined grains.

Gold — consume

  • Create surrogate-key dimensions and facts.
  • Keep historical dimension versions where useful.
  • Provide wide OBT access safely.
  • Pre-compute business summaries for dashboards.

3. Bronze layer schema

Bronze mirrors the incoming sources. The existing business columns remain unchanged. Production metadata is appended to make every record traceable to a pipeline run, source object and CDC/file event.

Bronze rule: if the source sends an email as " USER@MAIL.COM ", Bronze keeps that value. Trimming and lower-casing happen later in Silver. This makes replay and root-cause analysis possible.

4. Bronze-to-Silver data quality flow

Silver is the main data-quality layer. A successful Spark job is not enough; records must also satisfy the business rules needed by downstream analytics.

Bronze recordsRaw values + metadata
→
DQ checksStructure, completeness, format, references, ranges, reconciliation
→
Trusted SilverPass / pass with warning
Critical failureMissing key, invalid reference, impossible amount or structural failure
→
QuarantineRecord is retained for investigation and controlled reprocessing
DQ stageExamplesTypical action
FoundationMetadata present, valid JSON, required columns, datatype compatibilityReject structural failures or rescue unexpected fields.
CompletenessCustomer, product, order, order item, payment and review mandatory fieldsCritical missing keys are quarantined.
StandardisationFull name, email, phone, city, country code, status codes, timestampsConvert to a consistent Silver representation.
DeduplicationExact duplicates, latest mutable entity, duplicate review/event/catalog listingKeep the correct/latest valid business record.
Reference integrityOrder→customer, item→order, item→variant, payment→order, inventory→variantBlock or flag records that cannot be trusted.
Domain & rangePositive quantity, non-negative money, rating 1–5, valid inventory balanceCritical invalid values go to quarantine; warnings may remain flagged.
Business reconciliationOrder amount reconciliation and related customer/product/order relationship checksPrevent mathematically valid but business-incorrect data from reaching Gold.
EnrichmentAvailable inventory, verified purchase, product catalogue enrichment, order-line contextCreate reusable conformed business entities.
Severity matters: not every unusual value is rejected. A missing order_id is a critical failure. A statistical price outlier may be kept with a warning so the business can investigate it without losing the record.

10. How incremental processing works

Read the last successful watermark. The control table stores watermarks in one agreed timezone, preferably UTC.
Use a small overlap window for query-based CDC. Re-reading recent rows protects against late updates and clock skew. Bronze may therefore contain overlapping versions.
Append every extracted change to Bronze. The raw layer keeps what arrived rather than updating history in place.
Deduplicate in Silver by business key and sequence. Use source update time and ingestion time to select the latest trusted state.
Use defensive MERGE logic. A soft-delete for a key that never existed in Silver should not create a fake record.
Build Gold after Silver passes quality checks. Dimensions are resolved before facts, and summary outputs reuse canonical fact logic.
Advance the watermark only after success. The run audit and load-control tables record counts, window boundaries and status for safe retries.
Query-based CDC limitation: if a row changes three times between two extraction runs, a source table that stores only current state may expose only the final version. This pipeline therefore guarantees trusted latest-state analytics, not full transaction-log history.
